## Repository Checklist

If you are a contributor, this checklist helps you evaluate whether a project is ready to receive contributions.

**✅ A `README.md` file**

The README should link to or describe the following:

- Project purpose and context.
- Installation instructions.

**✅ A `CONTRIBUTING.md` file**

This guide explains how to contribute to the project. If none is available, you might find the contributing guide in the `README.md` file. A `CONTRIBUTING.md` file consists of the following:

- The recommended process for making issues and submitting pull requests.
  {/* prettier-ignore */}
- Ways to communicate with the maintainers.

**✅ A valid open source license**

Do not work on a project that does not have a license or does not use a standard open source license. See the <Link href="/resources/developer-resources/open-source/maintainer-guide#4-license">License</Link> section of our Maintainer Guide for resources about licenses.

**✅ A Code of Conduct (COC)**

Read the Code of Conduct (COC) to ensure you participate in a way that is consistent with the organization's guidelines.

## Guide to Writing Issues

There is no single best way to write an issue. But avoid anything that hides what you want or need, or that does not help the person who solves the issue.

Some important things to remember:

- **Provide information** <br />
  An issue needs information. Pictures, metrics, and more make it more precise than words alone.
- **Describe the issue** <br />
  Follow the organization's templates and ask yourself: What, Where, When, How, and Why. Describe the issue clearly, so that anyone can understand it without asking you for more details.
- **Do not solve the issue** <br />
  The maintainers do not expect you to solve the issue. If you want to solve it, comment to tell the maintainer that you want to work on it, and let them assign it to you.

A suggested solution can be especially helpful for less-experienced contributors. When writing issues on a repository that is not your own, you might need more context to provide the best solution. Remember that maintainers must review issues first and always have the final say in the solution or approach to the issue.

### Tips Before Writing an Issue

- Read the repository's `README.md` and `CONTRIBUTING.md` (if they have one) to learn how maintainers expect communication and how to create an issue. For example, some repositories require you to start a discussion before making an issue.
- Search current and closed issues to ensure no one has already written the issue you want to raise.
- If the organization has discussions enabled on their GitHub, search them to see if anyone has also mentioned the issue.
- Read the Code of Conduct (COC) to ensure you participate in a way that is consistent with the organization's guidelines. The absence of a COC is unfortunate, but it does not mean people should be rude or disrespectful, even if the issue is very frustrating.

### How to Create an Issue

This section walks you through how to create an issue, using the Virtual Coffee repository as an example.

1. Go to the [Virtual Coffee repository](https://github.com/Virtual-Coffee/virtualcoffee.io/).
2. Click the [**Issues**](https://github.com/Virtual-Coffee/virtualcoffee.io/issues/) tab.
3. Click the **New issue** button and see if a [designated template for your issue is available](https://github.com/Virtual-Coffee/virtualcoffee.io/issues/new/choose).
4. Click the button for the issue category that fits your needs. Then follow all the steps and requirements.

### How to Write an Issue

Remember, there is no single best way to write an issue. When the project does not provide a specific template, here is a list of what is good to share in different types of issues:

#### 🐞 Bug Issue

Include this information in the issue:

- **Title** <br />
  Clear enough to identify what the problem is about.
- **Screenshots** <br />
  Screenshots of the UI, logs, or anything that shows the problem exists.
- **Your setup** <br />
  The device and OS version, browser type and version you use, and any other setup that can help reproduce the problem.
- **Description** <br />
  Add the steps to reproduce the bug or behavior. Some things to consider:
  {/* prettier-ignore */}
		- What do you think the correct behavior _should_ be?
  {/* prettier-ignore */}
		- The current behavior and how it differs.
	{/* prettier-ignore */}
		- The conditions required to produce the bug. For example, the buttons or links you click.
- **Solution** <br />
  If you think of a solution to solve the problem, you can suggest something. However, the maintainer is the final decision-maker.
- **Links** <br />
  Issue or discussion that relates to this problem, if any.

#### 🌱 Feature Issue

- **Title** <br />
  Clear enough to identify what feature you want to add or see.
- **Description** <br />
  Describe why you wish to request the feature.
- **Proposed Solution** <br />
  What should the solution be and why? If you do not have a suggestion, that is fine too.
- **Links** <br />
  Issue or discussion related to this request, if any.

#### 📄 Documentation Issue

- **Title** <br />
  Clear enough to identify what the problem is about.
- **Description** <br />
  Describe why you request the documentation change. For example, "I noticed an unclear explanation of how to install the software in the installation section."
- **Proposed Solution** <br />
  What should the solution be and why? If you do not have a suggestion, that is fine too.

## Best Practices for Contributors

### Observing Repository Conventions

Most repositories have certain conventions that you need to follow. These differ from project to project. You can usually find them in the `README.md` or `CONTRIBUTING.md` files. The areas they cover vary, but there are common things to look out for:

- Code or documentation style guides
- General conventions for communicating
- Branch naming conventions
- Git workflows

### Using AI Assistance

These conventions may also include expectations for contributions created with AI assistance, such as whether you need to disclose its use. Follow the project's guidance when it is available. Whether or not you use AI assistance, you are responsible for every contribution you submit. Make sure you understand the changes, verify that they are accurate, and test them as the project requires. Don't submit work you haven't reviewed or can't explain.

### The Work Process

Most projects expect some form of discussion before making a pull request. Expectations vary from project to project. But you can usually find them in the `README.md` or `CONTRIBUTING.md` files.

Many projects use labels such as `bug`, `documentation`, `help wanted`, `ready for dev`, and many more to help determine what issues you can work on.

Unless the documentation says otherwise, you should comment on an issue you want to work on. Ask the maintainer to assign you to it, and only start working on it when they give it to you. It helps avoid duplicated work and keeps expectations aligned. Do not open a pull request unless the repository explicitly accepts unsolicited pull requests.

### Communication with Maintainers

Communication is key to working on open source. Most projects have communication conventions, and contributors should always follow these rules. Many projects primarily communicate via comments on issues or pull requests. Some projects have external groups such as Slack, a forum, IRC, or email lists where people communicate and coordinate work. If the project uses these, there should be information in the `README.md` or `CONTRIBUTING.md` files. Without specific details on where to communicate, you can assume that communication can occur via comments on issues or pull requests. Write your own comments and pull request descriptions so maintainers know they are talking to you and can trust that you understand your contribution.

Regardless of the tools you use, keep these things in mind to make communication effective and respectful, especially in an international online space.

- **Always follow the Code of Conduct (COC)** <br />
  Yes, always, even if you disagree with its contents or think it restricts your freedom of speech. The community agreed on these rules to govern the space. As a member of the community, you must follow these rules.
- **Keep messages short and straightforward** <br />
  It is often best to write 'one message, one topic'. Sometimes this is not possible, for example, when you are unavailable for some time and need to respond to several points. If you need to discuss several topics in one message, put each in a separate paragraph.
- **Keep the conversation respectful** <br />
  Disagreement and debate are healthy, but it is important to keep the conversation respectful. You can challenge ideas, but do not criticize the person directly.
- **Low-context communication in international, cross-cultural spaces** <br />
  Make your meaning explicit in the words you use. People from different cultures might not understand specific cultural references, clichés, and sayings.

### Self-Care

We recommend you approach open source work with the same professionalism as you would work for an employer. Take care of things such as code style, documentation, and testing, just as you would in your work for an employer.

But remember, you are doing this in your spare time, and self-care is essential. It is okay if you cannot work at a fast pace. Both you and the maintainer should set reasonable expectations from the beginning.

You should have enough time to work at a relaxed pace. Maintainers should not expect you to complete the work by a strict deadline, even for non-trivial issues.
