## Definitions

### What Is Git?

We like this Git definition from [Amazon Web Services](https://aws.amazon.com/devops/source-control/git/):

<blockquote className="blockquote border-start border-4 ps-3">
	Git is a distributed, open-source version control system (VCS) that enables
	you to store code, track revision history, merge code changes, and revert to
	an earlier version of the code when needed.
</blockquote>

### What Is GitHub?

Like GitLab and Bitbucket, GitHub is a platform for hosting, sharing, and collaborating on Git repositories. You can interact with it via the [GitHub website](https://github.com) or [GitHub CLI](https://cli.github.com) if you prefer the command line.

</TextContainer>

## Contributing to Open Source with Git and GitHub

### Forking a Repository

To contribute to an open source project, first fork the repository to your GitHub account.
Most open source projects do not allow you to make and push changes directly in their repository. That is why you fork the repository.

Forking means you create a copy of the repository in your GitHub account to make changes without pushing commits directly to the project's original repository.

To fork a repository:

1. Click the **Fork** button on the project's repository page on GitHub.
2. GitHub redirects you to the "Create a new fork" page. Click the **Create fork** button.

By convention, you call this forked repository the `origin` repository.

### Authenticating with GitHub

If you use GitHub on your local computer for the first time, authenticate your local Git with GitHub before you clone a repository.

You must provide your email and credentials whenever you clone a repository, commit and push changes, or do other Git activities related to GitHub locally.
That is a way for GitHub to authenticate you as a user.
But you can set up your credentials locally, so you do not have to input them whenever you do a Git activity.

How you authenticate depends on how you clone the repository. The next section describes the options.

### Cloning a Repository

After you fork a project's repository, you need to clone your fork. Cloning means creating a copy of a GitHub repository on your local computer for you to work with.

In the **Clone** box on the **Local** tab, GitHub offers three ways to clone a repository:

- **[HTTPS](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#https)** <br/>
  It is the most common one to use. You must create a [Personal Access Token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) to enter when GitHub prompts for your password.

- **[SSH (Secure Shell)](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#ssh)** <br/>
  It provides an encrypted way to exchange information safely. To use SSH, follow [GitHub's guide to generating a new SSH key](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

- **[GitHub CLI](https://cli.github.com)** <br/>
  It gives you a command to run in your terminal. This option requires that you install GitHub CLI.

To clone a repository:

1. Go to your forked repository on GitHub.
2. Click the **Code** button.
3. On the **Local** tab, select **HTTPS**. You can also select **SSH** or **GitHub CLI**, but this example uses HTTPS.
4. Copy the URL.
5. In your terminal, run:

   ```bash
   git clone REPO-URL
   ```

   Change `REPO-URL` to the copied URL of the forked repository.

### Adding an `upstream` Remote Repository

Even though you have cloned the forked repository, you may also want to add the original repository as one of your remote repositories.
By convention, you call this original repository `upstream`. By doing this, you can pull other people's changes into your local repository whenever you need to.

1. Add the original repository as a remote repository:

   ```bash
   git remote add upstream REPO-URL
   ```

   Change `REPO-URL` to the URL of the original repository.

2. Verify that Git added both remote repositories:

   ```bash
   git remote -v
   ```

   The command lists your remote repositories. You see `origin` (your fork) and `upstream` (the original repository).

Now you are ready to work on the changes.

### Creating a New Branch

Before you change anything, create a new branch. Do not work directly in the default branch. Most repositories name the default branch `main` or `master`, but the name can differ.

To create a new branch, run this command in your terminal:

```bash
git checkout -b BRANCH-NAME
```

Change `BRANCH-NAME` to a name for your branch. Name it after your changes, for example, `fix/typo-readme` or `feat/add-dark-theme`.

### Adding and Committing Changes

When you finish making changes, add and commit them before you push them to GitHub. To do so:

1. Add your changes to the Git staging area. To add all new and modified files, run:

   ```bash
   git add .
   ```

   To add a specific directory or file instead, run this command:

   ```bash
   git add PATH
   ```

   Change `PATH` to the path of the directory or file that you want to add. For example:

   ```bash
   git add styles/header.css
   ```

2. Save your changes by committing them:

   ```bash
   git commit -m "COMMIT-MESSAGE"
   ```

   Change `COMMIT-MESSAGE` to a short description of your changes. For example:

   ```bash
   git commit -m "feat: add navbar and footer"
   ```

3. Verify that you added and committed your changes:

   ```bash
   git status
   ```

   This command shows the state of your Git working directory and staging area.

### Fetching `upstream` Changes

While you work on your changes locally, someone else may change the same file. That person may already have their pull request merged into the default branch, such as `main`, of the `upstream` repository.
Always make sure that your fork is up to date with the `upstream` repository.

1. Go to your forked repository on GitHub.
2. Click the **Sync fork** button.
3. If you see an **Update branch** button, click it. If you do not, your fork has no new changes. In that case, <Link href="/resources/developer-resources/open-source/git-101#pushing-changes">push your changes</Link>. Then <Link href="/resources/developer-resources/open-source/git-101#making-a-pull-request">make a pull request</Link>.

Now your fork has the same update as the `upstream` repository.

### Synchronizing Changes Locally

Now that your `origin` repository is in sync with the `upstream`, synchronize these changes locally. That way, you already have the most recent content when you push your changes.

Fetch and merge the latest update into your working branch.
In your terminal, make sure that you are in your working branch. Then run:

```bash
git pull origin DEFAULT-BRANCH
```

Change `DEFAULT-BRANCH` to the name of the repository's default branch. It is not always `main` or `master`. Repositories can use other names.

The command fetches the updated default branch from the `origin` repository and merges it into your local working branch.

If merge conflicts occur, resolve them. The next section explains how.

### Resolving Merge Conflicts

It is common to encounter merge conflicts when contributing to open source.
Conflicts usually occur when two different branches change the same lines in the same files.

You may get conflicts if you push your changes before you fetch `upstream` and synchronize it with your `origin` and local repositories.
When you are about to create a pull request on GitHub, GitHub notifies you about the conflicts, if any.

There are two ways to resolve conflicts:

1. **Directly on GitHub**

   GitHub shows a prompt that your branch has conflicts that you must resolve. Click the **Resolve conflict** button and fix the conflicts.

   ![A GitHub pull request page showing conflicting files and a Resolve conflicts button](https://cdn.hashnode.com/res/hashnode/image/upload/v1646421795534/cuEiIEKgT.JPG)

2. **In the local environment**
   - Complete the steps in <Link href="/resources/developer-resources/open-source/git-101#fetching-upstream-changes">Fetching `upstream` Changes</Link> and <Link href="/resources/developer-resources/open-source/git-101#synchronizing-changes-locally">Synchronizing Changes Locally</Link>.<br />
     Then your text editor shows this:

     ![A text editor showing a merge conflict with options to accept the current change, the incoming change, or both](https://cdn.hashnode.com/res/hashnode/image/upload/v1662321487768/YXuwvPrzz.jpg)

     <br />

   - Select one of the options:
     - **Accept Current Change** — when you _only_ want to keep your change.
     - **Accept Incoming Change** — when you _only_ want to keep the incoming change.
     - **Accept Both Changes** — when you want to _keep both_ your changes and the incoming changes.

After resolving the conflicts, fix and adjust the code if necessary. Then <Link href="/resources/developer-resources/open-source/git-101#adding-and-committing-changes">add and commit the changes</Link>.

### Pushing Changes

You have fetched and synchronized updates and also added and committed the changes. Now push your changes to the `origin` repository.

To do so, run this command in your terminal:

```bash
git push origin BRANCH-NAME
```

Change `BRANCH-NAME` to the name of your working branch.

### Making a Pull Request

Once you have pushed your changes to the `origin` repository, you can submit the changes to the `upstream` repository by making a pull request.

Creating a pull request allows the maintainers to review your work, comment, and request any necessary changes. They then decide whether to merge your changes into the project codebase.

To make a pull request:

1. Go to the `upstream` repository on GitHub and click the **New pull request** button. If you have recently pushed changes to GitHub, a banner at the top of the page shows a **Compare and pull request** button. Click it.
2. GitHub takes you to the "Open pull request" form, where you write a description of your pull request. Many projects provide a pull request template in the form. If the project does not, read its contributing guidelines (usually in the `CONTRIBUTING.md` file) and follow the conventions described there.
3. When you are ready, click the **Create pull request** button.

You have made your pull request.

If a maintainer requests changes, you can make the requested changes and push new commits to the same branch. GitHub adds them to the pull request automatically.

## Advanced Git and GitHub Workflows

<LeadText>

The following workflows are helpful when collaborating with another person in open source.

</LeadText>

### Collaborating Asynchronously on a Shared Branch Between Two Different Forks

You and your teammate, Alice, each forked the same repository. You work on the same issue in the same file, but not at the same time. Each of you follows the same steps.

This example shows your point of view. To collaborate:

1. Add Alice's fork as a remote repository:

   ```bash
   git remote add alice REPO-URL
   ```

   Change `REPO-URL` to the URL of Alice's fork. This example uses `alice` as the name of the remote repository, but you can use any name.

2. Fetch Alice's branches:

   ```bash
   git fetch alice
   ```

3. Go to the target branch:

   ```bash
   git checkout BRANCH-NAME
   ```

   Change `BRANCH-NAME` to the name of the target branch at Alice's fork.

4. Pull the changes that Alice pushed:

   ```bash
   git pull alice BRANCH-NAME
   ```

Now you have the updated branch with the changes from your teammate.

You or Alice can submit the pull request when you both finish the work.
Each commit contains the name of its author, so GitHub credits both contributions.

### Collaborating Synchronously

When you work at the same time with Alice and Charlie on the same issue, use the same steps as in the asynchronous collaboration above. The only difference is that you [add them as co-authors in your commit message](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors).

To add co-authors:

1. Start your commit message with a short description of the change. Press Enter twice to leave a blank line after it.
2. Add one `Co-authored-by:` line for each teammate, in this format:

   ```bash
   git commit -m "feat: add new feature
   >
   >
   Co-authored-by: Alice <alice@email.com>
   Co-authored-by: Charlie <charlie@email.com>"
   ```

   Change the names and email addresses to your teammates' details. Use the email address associated with each teammate's GitHub account.

3. Close the commit message with a double quote (") at the end of the last `Co-authored-by:` line. Do not close it earlier.

You do not need to add your own name, because you are the one who commits the changes.

## Getting the Most Out of Your GitHub Profile

You can customize your GitHub profile. Add a short bio, a website, and social media links. Pin the repositories that show your best work. Your profile then works like a mini portfolio.

	src="/assets/images/developer-resources/open-source/github-profile-example.png"

### How Does It Work?

To customize your profile, create a repository in your account with the same name as your GitHub username and add a README file. GitHub renders the contents of that README file on your profile page. You can add many kinds of integrations to this README, such as stats, badges, and your latest blog posts.
