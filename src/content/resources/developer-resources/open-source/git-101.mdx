## Definitions

### What Is Git?

See this Git definition from [Amazon Web Services](https://aws.amazon.com/devops/source-control/git/):

<blockquote className="blockquote border-start border-4 ps-3">
	Git is a distributed, open-source version control system (VCS) that enables
	you to store code, track revision history, merge code changes, and revert to
	an earlier version of the code when needed.
</blockquote>

### What Is GitHub?

Like GitLab and Bitbucket, GitHub is a platform for hosting, sharing, and collaborating on Git repositories. You can interact with it through the [GitHub website](https://github.com) or [GitHub CLI](https://cli.github.com) if you prefer the command line.

If you are new to open source, see the <Link href="/resources/developer-resources/open-source/git-101#glossary">Glossary</Link> at the end of this guide. It explains open source terms in plain English.

</TextContainer>

## Contributing to Open Source with Git and GitHub

### Forking a Repository

To contribute to an open source project, first fork the repository to your GitHub account.
Most open source projects do not allow you to make and push changes directly in their repository. That is why you fork the repository.

Forking means you create a copy of the repository in your GitHub account to make changes without pushing commits directly to the project's original repository.

To fork a repository:

1. Click the **Fork** button on the project's repository page on GitHub.

   <img
   	src="/assets/images/developer-resources/open-source/github-fork-button.png"
   	alt="The Fork button, with the number of forks, between the Unwatch and Star buttons on a GitHub repository page"
   	width="412"
   	height="60"
   />

2. GitHub redirects you to the "Create a new fork" page. Fill in the required fields, then click the **Create fork** button.

   <img
   	src="/assets/images/developer-resources/open-source/github-create-a-new-fork-page.png"
   	alt='The "Create a new fork" page with the Owner and Repository name fields, a Description field, the "Copy the main branch only" checkbox, and the Create fork button'
   	width="600"
   	height="418"
   />

When you clone your fork, Git names it `origin`. This page refers to your fork as the `origin` repository.

### Authenticating with GitHub

If you use GitHub on your local computer for the first time, authenticate your local Git with GitHub before you push changes.

Git asks for your credentials when you push changes to GitHub.
You can save your credentials on your computer, so you do not have to enter them every time.

How you authenticate depends on how you clone the repository. The next section describes the options.

### Cloning a Repository

After you fork a project's repository, you need to clone your fork. Cloning means creating a copy of a GitHub repository on your local computer for you to work with.

In the **Clone** box on the **Local** tab, GitHub offers three ways to clone a repository:

- **[HTTPS](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#https)** <br />
  It is the most common option. When Git asks for your username and password, enter your GitHub username and a [Personal Access Token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens). GitHub no longer accepts your account password for Git.

- **[SSH (Secure Shell)](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#ssh)** <br />
  It provides an encrypted way to exchange information safely. To use SSH, follow [GitHub's guide to generating a new SSH key](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

- **[GitHub CLI](https://cli.github.com)** <br />
  It gives you a command to run in your terminal. This option requires that you install GitHub CLI.

To clone a repository:

1. Go to your forked repository on GitHub.
2. Click the **Code** button.
3. On the **Local** tab, select **HTTPS**. You can also select **SSH** or **GitHub CLI**, but this example uses HTTPS.
4. Copy the URL.

   <img
   	src="/assets/images/developer-resources/open-source/code-button-clone-tabs-github.png"
   	alt="The Code menu on a GitHub repository page with the Local tab open. The Code button, the HTTPS tab, and the copy button next to the repository URL are marked"
   	width="412"
   	height="385"
   />

5. In your terminal, run:

   ```bash
   git clone REPO-URL
   ```

   Change `REPO-URL` to the copied URL of the forked repository.

### Adding an `upstream` Remote Repository

After you clone your fork, add the original repository as a remote repository.
By convention, you call this original repository `upstream`. With this remote repository, you can pull other people's changes into your local repository from your terminal.
The steps on this page sync your fork on GitHub instead, so this step is optional.

1. Add the original repository as a remote repository:

   ```bash
   git remote add upstream REPO-URL
   ```

   Change `REPO-URL` to the URL of the original repository.

2. Verify that Git added both remote repositories:

   ```bash
   git remote -v
   ```

   The command lists your remote repositories. You see `origin` (your fork) and `upstream` (the original repository).

Now you are ready to work on the changes.

### Creating a New Branch

Before you change anything, create a new branch. Do not work directly in the default branch. Most repositories name the default branch `main` or `master`, but the name can differ.

To create a new branch, run this command in your terminal:

```bash
git checkout -b BRANCH-NAME
```

Change `BRANCH-NAME` to a name for your branch. Name it after your changes, for example, `fix/typo-readme` or `feat/add-dark-theme`.

### Adding and Committing Changes

When you finish making changes, add and commit them before you push them to GitHub. To do so:

1. Add your changes to the Git staging area. To add all new and modified files, run:

   ```bash
   git add .
   ```

   To add a specific directory or file instead, run this command:

   ```bash
   git add PATH
   ```

   Change `PATH` to the path of the directory or file that you want to add. For example:

   ```bash
   git add styles/header.css
   ```

2. Save your changes by committing them:

   ```bash
   git commit -m "COMMIT-MESSAGE"
   ```

   Change `COMMIT-MESSAGE` to a short description of your changes. For example:

   ```bash
   git commit -m "feat: add navbar and footer"
   ```

3. See the state of your working directory and staging area:

   ```bash
   git status
   ```

   If you added and committed all your changes, the output says `nothing to commit, working tree clean`.

### Syncing Your Fork with `upstream`

While you work on your changes locally, someone else may change the same file. That person may already have their pull request merged into the default branch, such as `main`, of the `upstream` repository.
Always make sure that your fork is up to date with the `upstream` repository.

1. Go to your forked repository on GitHub.
2. Click the **Sync fork** button.
3. If you see an **Update branch** button, click it.

   <img
   	src="/assets/images/developer-resources/open-source/sync-fork-github.png"
   	alt='The Sync fork button, marked, on a forked repository page that is 3 commits behind. The open menu says "This branch is out-of-date" and shows the Compare button and the marked Update branch button'
   	width="600"
   	height="174"
   />

   If you do not see the button, your fork has no new changes. In that case, <Link href="/resources/developer-resources/open-source/git-101#pushing-changes">push your changes</Link>. Then <Link href="/resources/developer-resources/open-source/git-101#making-a-pull-request">make a pull request</Link>.

Now your fork has the same updates as the `upstream` repository.

### Synchronizing Changes Locally

Now that your `origin` repository is in sync with the `upstream` repository, synchronize these changes locally. That way, you already have the most recent content when you push your changes.

Fetch and merge the latest update into your working branch. To do so:

1. In your terminal, make sure that you are in your working branch.
2. Run:

   ```bash
   git pull origin DEFAULT-BRANCH
   ```

   Change `DEFAULT-BRANCH` to the name of the repository's default branch.

The command fetches the updated default branch from the `origin` repository and merges it into your local working branch.

If merge conflicts occur, resolve them. The next section explains how.

### Resolving Merge Conflicts

It is common to encounter merge conflicts when contributing to open source.
Conflicts usually occur when two different branches change the same lines in the same files.

You may get conflicts if you do not sync your branch with the `upstream` repository before you open a pull request.
When you open a pull request, GitHub shows a message about conflicts, if any.

You can resolve simple conflicts, where two branches change the same lines, in GitHub's web editor. For more complex conflicts, GitHub does not let you use the web editor. In that case, resolve the conflicts in your local repository.

#### Resolving Simple Conflicts on GitHub

1. On the pull request page, GitHub shows the message "This branch has conflicts that must be resolved". Click the **Resolve conflicts** button.

   <img
   	src="/assets/images/developer-resources/open-source/merge-conflicts-github.png"
   	alt='The message "This branch has conflicts that must be resolved" on a pull request, with two conflicting files listed and the Resolve conflicts button marked'
   	width="600"
   	height="158"
   />

2. In the editor, GitHub shows the conflicting files on the left. For each conflict, click one of the options above it.

   <img
   	src="/assets/images/developer-resources/open-source/github-resolve-conflicts.png"
   	alt='The GitHub conflict editor for README.md, with "2 conflicting files" on the left and "2 conflicts" at the top. The options Accept current change, Accept incoming change, and Accept both changes are above the conflict, and the Mark as resolved button is at the top right'
   	width="800"
   	height="156"
   />

   The options work as follows:

   - **Accept current change** — when you _only_ want to keep your change.
   - **Accept incoming change** — when you _only_ want to keep the incoming change.
   - **Accept both changes** — when you want to _keep both_ your changes and the incoming changes.

   You can also edit the file by hand. Keep the lines that you want, and delete the markers `<<<<<<<`, `=======`, and `>>>>>>>`.

3. Click the **Mark as resolved** button. Repeat for each conflicting file.
4. Click the **Commit merge** button.

After you commit the merge, pull the updated branch to your local repository before you continue to work on it.

#### Resolving Conflicts Locally

1. Complete the steps in <Link href="/resources/developer-resources/open-source/git-101#syncing-your-fork-with-upstream">Syncing Your Fork with `upstream`</Link> and <Link href="/resources/developer-resources/open-source/git-101#synchronizing-changes-locally">Synchronizing Changes Locally</Link>.
2. If `git pull` reports conflicts, open the conflicting files in your text editor. This example uses Visual Studio Code:

   <img
   	src="/assets/images/developer-resources/open-source/conflict-lines-vscode.png"
   	alt="A text editor showing conflict markers around two versions of the same line, with the options Accept Current Change, Accept Incoming Change, Accept Both Changes, and Compare Changes marked above them"
   	width="800"
   	height="109"
   />

3. For each conflict, click **Accept Current Change**, **Accept Incoming Change**, or **Accept Both Changes**. They have the same meaning as the options on GitHub.
4. Save the file. Repeat for each conflicting file.
5. When you resolve all the conflicts, <Link href="/resources/developer-resources/open-source/git-101#adding-and-committing-changes">add and commit the changes</Link>.

### Pushing Changes

After you sync your branch and commit your changes, push your branch to the `origin` repository.

To do so, run this command in your terminal:

```bash
git push origin BRANCH-NAME
```

Change `BRANCH-NAME` to the name of your working branch.

### Making a Pull Request

After you push your changes to the `origin` repository, you can submit the changes to the `upstream` repository by making a pull request.

A pull request allows the maintainers to review your work, comment, and request any necessary changes. They then decide whether to merge your changes into the project codebase.

To make a pull request:

1. Go to the `upstream` repository on GitHub. If you recently pushed changes, a banner at the top of the page shows a **Compare & pull request** button. Click it.
2. If you do not see the banner, click the **New pull request** button instead.
3. GitHub takes you to the "Open a pull request" form, where you write a description of your pull request. Many projects provide a pull request template in the form. If the project does not, read its contributing guidelines (usually in the `CONTRIBUTING.md` file) and follow the conventions described there.
4. When you are ready, click the **Create pull request** button.

You have made your pull request.

If a maintainer requests changes, you can work on the requested changes and push new commits to the same branch. GitHub adds them to the pull request automatically.

### Collaborating Asynchronously on a Shared Branch Between Two Different Forks

You and your teammate, Alice, each forked the same repository. You work on the same issue in the same file, but not at the same time. Each of you follows the same steps.

This example shows your point of view. To collaborate:

1. Add Alice's fork as a remote repository:

   ```bash
   git remote add alice REPO-URL
   ```

   Change `REPO-URL` to the URL of Alice's fork. This example uses `alice` as the name of the remote repository, but you can use any name.

2. Fetch Alice's branches:

   ```bash
   git fetch alice
   ```

3. Create a local branch from Alice's branch and go to it:

   ```bash
   git checkout -b BRANCH-NAME alice/BRANCH-NAME
   ```

   Change both `BRANCH-NAME` to the name of the target branch at Alice's fork. If you used a different name for the remote repository in step 1, change `alice` to that name.

4. Later, pull new changes that Alice pushed:

   ```bash
   git pull alice BRANCH-NAME
   ```

   Run this command each time Alice pushes new commits.

Now you have the updated branch with the changes from your teammate.

You or Alice can submit the pull request when you both finish the work.
Each commit contains the name of its author, so GitHub credits both contributions.

### Collaborating Synchronously

When you work at the same time with Alice and Charlie on the same issue, use the same steps as in the previous section. The only difference is that you [add them as co-authors in your commit message](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors).

To add co-authors:

1. Start your commit message with a short description of the change. Press **Enter** twice to leave a blank line after it.
2. Add one `Co-authored-by:` line for each teammate, in this format:

   ```bash
   git commit -m "feat: add new feature
   >
   >
   Co-authored-by: Alice <alice@example.com>
   Co-authored-by: Charlie <charlie@example.com>"
   ```

   Change the names and email addresses to your teammates' details. Use the email address associated with each teammate's GitHub account.

   When you press **Enter** inside the quotes, the terminal shows `>` at the start of the new line. Do not type it.

3. Close the commit message with a double quote (`"`) at the end of the last `Co-authored-by:` line. Do not close it earlier.

You do not need to add your own name, because you are the one who commits the changes.

## Getting the Most Out of Your GitHub Profile

You can customize your GitHub profile. Add a short bio, a website, and social media links. Pin the repositories that show your best work. Your profile then works like a mini portfolio.

### How It Works

To customize your profile, create a repository in your account with the same name as your GitHub username and add a README file. GitHub renders the contents of that README file on your profile page. You can add many kinds of integrations to this README, such as stats, badges, and your latest blog posts.

## Glossary

<LeadText>

These are common terms used in open source.

</LeadText>

<p className="h5 mt-4 mb-2">B</p>

- **Branch**: A separate version of a repository. Changes on a branch do not affect other branches, such as the default branch, until you merge them.

<p className="h5 mt-4 mb-2">C</p>

- **Clone**: A copy of a repository on your computer, or the action of making that copy.
- **Co-author**: A person who shares credit for a commit.
- **Commit**: A saved record of your project's changes.
- **Commit message**: A short text that explains what a commit changes.
- **Contributor**: Anyone who adds something to a project, such as code, documentation, design, or help.

<p className="h5 mt-4 mb-2">D</p>

- **Default branch**: The branch that GitHub treats as the main one for a repository. Accepted changes are usually merged into it, and new pull requests target it unless you choose another branch.

<p className="h5 mt-4 mb-2">F</p>

- **Fetch**: Download new changes from a remote repository without changing your files.
- **Fork**: Your own copy of another person's repository on your GitHub account.

<p className="h5 mt-4 mb-2">I</p>

- **Issue**: A task, bug report, idea, or question about a repository. Each issue has its own discussion.
- **Issue template**: A form with prompts that helps people write a clear issue.

<p className="h5 mt-4 mb-2">L</p>

- **Label**: A tag on an issue or pull request that helps people sort and find it.
- **Local repository**: The copy of a repository on your computer.

<p className="h5 mt-4 mb-2">M</p>

- **Maintainer**: A person who manages a repository. They review changes and decide what to merge.
- **Merge**: Take the changes from one branch and add them to another branch.
- **Merge conflict**: A problem that happens when two branches change the same line of a file, or when one person edits a file and another person deletes it.

<p className="h5 mt-4 mb-2">O</p>

- **Origin**: The default name Git gives to the remote repository that you cloned from. When you clone your fork, `origin` is your fork.

<p className="h5 mt-4 mb-2">P</p>

- **Pull**: Download new changes from a remote repository and add them to your current branch.
- **Pull request**: A request to add your changes to a repository. Maintainers review it and then accept or reject it.
- **Pull request template**: Text that appears in a new pull request and helps people describe their changes.
- **Push**: Send your commits from your computer to a remote repository.

<p className="h5 mt-4 mb-2">R</p>

- **Remote repository**: A copy of a repository that is stored on a server, usually GitHub. You can connect it to your local repository to share changes.
- **Repository**: A project folder that Git tracks. It holds all the project files and the history of every change to them.
- **Review**: Feedback on a pull request. A maintainer or a reviewer can comment, approve the changes, or request changes before the pull request is merged.

<p className="h5 mt-4 mb-2">S</p>

- **Staging area**: A place where you collect the changes that you want to save in your next commit.
- **Sync a fork**: Update your fork with the latest changes from `upstream`. GitHub has a **Sync fork** button for this.

<p className="h5 mt-4 mb-2">T</p>

- **Triage**: Sort new issues and decide if they are worth working on. Maintainers often add labels, ask for more details, or close duplicates.

<p className="h5 mt-4 mb-2">U</p>

- **Upstream**: The name people usually give to the original repository that you forked from. It is a convention, and you must add this remote repository yourself.

</TextContainer>
