## Preparing a Project for Open Source Contributions

<LeadText>

This section addresses the **minimum** requirements, highlighting key areas and considerations to help you evaluate whether or not your open source project is ready for contributions. When Virtual Coffee determines the projects we highlight and recommend to our members, these are the things we look for and why. We hope it can serve as a guide to anyone who finds this document.

</LeadText>

### Name, Description, Topics

We start with the natural beginning for evaluating an open source project: the descriptive fields that GitHub provides. These are the first and most straightforward ways GitHub uses to recommend your content to potential contributors.

- It should have a relevant name.
- It should have a description clearly describing what the project does and is for.
- It should have relevant topics highlighting its scope, stack, field, etc.

An example of a good name, description, and topics:

### Documentation

Good documentation is the best indicator that a project is well maintained and supported, and has a healthy and active community. There are many materials a repository can use to provide context to potential contributors, but the docs that matter most are:

#### 1. README

The README is the main page of your repository. It is the first thing anyone sees after the name and description, and it is the central place for all content, links, docs, and other project associations. A project with a README is usually ready to accept contributions. Some basic things you should include in your README are:

- A more detailed project description than the description field on GitHub.
- How to install and run your application, with a link to the documentation that explains it, if any. The more detailed, the better.
- A link to the Code of Conduct.
- Project status, roadmap, and other pertinent details for those interested in using or contributing to the project.

🔎 **Example**: [Virtual Coffee's README](https://github.com/Virtual-Coffee/virtualcoffee.io/blob/main/README.md)

#### 2. Code of Conduct

The Code of Conduct (COC) is an excellent indicator of a healthy contributor's environment. There are many Code of Conduct styles online, and many projects use one of the standard templates. But it is always worth looking at a project's Code of Conduct before starting any contribution work. Not every open source project has one. Some maintainers opt to describe appropriate behavior in the README file.

🔎 **Example**: [Virtual Coffee's Code of Conduct](https://github.com/Virtual-Coffee/.github/blob/main/CODE_OF_CONDUCT.md)

#### 3. Contributing Guidelines

Finally, explain how to contribute to the project. Some maintainers write these instructions directly in the README, which is fine. Still, we prefer explicit guidelines that answer these questions:

- What is the recommended process for making issues and submitting pull requests?
- What should someone do if they feel somebody violates the Code of Conduct?
- How can contributors communicate with maintainers, for example, through GitHub issues, a chat platform, or email?
- How long should contributors expect responses and reviews?
- Can contributors use AI assistance, and what are the expectations for disclosure, testing, or review?

Each project should decide what approach to AI-assisted contributions fits its goals, community, and maintenance capacity. Document those expectations in the contributing guidelines or README so contributors know what is acceptable before they begin their work. The expectations don't need to be the same across projects, but they should be clear and easy to find, giving maintainers something to point to when closing low-effort submissions that don't meet the project's standards.

🔎 **Example**: [Virtual Coffee's Contributing Guide](https://github.com/Virtual-Coffee/virtualcoffee.io/blob/main/CONTRIBUTING.md)

#### 4. License

Many [popular and vetted open source licenses](https://opensource.org/licenses) make it easy and safe for people to contribute to a particular project. Unless you are a lawyer or have access to one, use one of these licenses.

🔎 **Example**: [Virtual Coffee's open source license](https://github.com/Virtual-Coffee/virtualcoffee.io/blob/main/LICENSE)

### Issue and Pull Request Templates

These templates guide potential contributors in creating issues and pull requests to the project. They spare the maintainer and the contributor from guessing the appropriate procedure for these contributions.

![Templates](https://user-images.githubusercontent.com/13292886/132138524-0a38d35c-305e-4804-ba36-e7adfa73e09d.png)

🔎 **Example**: Virtual Coffee's [issue templates](https://github.com/Virtual-Coffee/virtualcoffee.io/tree/main/.github/ISSUE_TEMPLATE) and [pull request template](https://github.com/Virtual-Coffee/virtualcoffee.io/blob/main/.github/PULL_REQUEST_TEMPLATE.md)

### Beginner Friendliness

To make your project beginner-friendly, indicate this in your documentation and processes:

- **Call to action** <br />
  Some repositories mention 'contributions welcome' or 'beginner friendly' in the
  README, or have labels on issues for beginners. Either way, there should be some indication that you do want someone to help.
- **Healthy interactions with contributors** <br />
  Unless a project is brand new, it likely has some history of contributions from others. Looking at those interactions and how the maintainers work with contributors is a great way for contributors to get a sense of the project. How often do maintainers respond? How do they respond? Do maintainers appreciate contributors for their work? If you intend to make your project beginner-friendly, keep this in mind.
- **Clear labeling system in issues** <br />
  The easier it is to navigate the project issues and resources, the more friendly it is for new contributors.

Everyone has a slightly different definition of 'beginner friendly', so the experience may vary in different projects, which is okay.

### Open Sourcing a Project without Expecting Contributions

If you want to open source your project so that other people can freely use your work, you do not have to do everything on the checklist.

For example, you do not need issue and pull request templates or a contributing guide. A Code of Conduct, however, is still recommended. Even if you are not expecting contributions, you may still get public activity on your repository, for example, on issues. A Code of Conduct helps you set boundaries and keep conversations respectful.

## Best Practices for Maintainers

### Communication with Contributors

Communication is key to running a successful open source project. Establish conventions for communication early on and document them clearly. Many projects communicate via issues and pull requests. Some use external platforms such as Slack, a forum, IRC, or email lists. All are good ways to communicate. The important thing is to decide what works for your project. Using issues and pull requests is a solid choice if you are not sure what works best.

If you maintain a company project that is open to external contributors, coordinate internal and external communication. That way, outside contributors get the essential updates that the company shares internally.

Regardless of the tools you use, keep these things in mind to make communication effective and respectful, especially in an international online space.

- **Have a Code of Conduct** <br />
  All communication should follow the Code of Conduct.
- **Keep messages short and straightforward** <br />
  It is often best to write 'one message, one topic'. Sometimes this is not possible, for example, when you are unavailable for some time and need to respond to several points. If you need to discuss several topics in one message, put each in a separate paragraph.
- **Keep the conversation respectful** <br />
  Disagreement and debate are healthy, but it is important to keep the conversation respectful. You can challenge ideas, but do not criticize the person directly.
- **Low-context communication in international, cross-cultural spaces** <br />
  Make your meaning explicit in the words you use. People from different cultures might not understand specific cultural references, clichés, and sayings.

### Managing Expectations

Managing the expectations of maintainers and contributors helps a project run smoothly with external contributors.

Here are several things you can do to help manage expectations:

- Break down tasks for external contributors into small, well-defined chunks.
- Make sure the contributing guide or README clearly explains any preferences for code style, branch names, Git workflows, etc.
- Tell contributors what support you can provide, if any, such as pair programming or answering questions during office hours.
- Share your availability and the expected time to review pull requests.

### Building Community

A strong community around an open source project can be crucial to the project's success. An active community around an open source project helps the maintainers handle support, spread the word, and bring new users and contributors to the project. It also allows maintainers to get feedback and new ideas to help the project fulfill the needs and aspirations of users.

Building a community takes effort and is as important as the technical development effort. It involves tools that support the community. It also involves making and nurturing connections with and between people.

Things that help build community:

- **A place for discussion** <br />
  It could be GitHub issues for smaller projects where the community focuses on project questions and development discussions. For larger projects or if you want to build a community in a broader sense, a separate venue such as a Slack or Discord community or forum works better.
- **A Code of Conduct** <br />
  It sets boundaries for interaction and keeps the community a welcoming space for everyone.
- **Community documentation** <br />
  It explains how the community works and where to find things related to the community. For example, Virtual Coffee has the <Link href="/resources/virtual-coffee-handbook/">Virtual Coffee Handbook</Link>.
- **Leading with empathy and kindness** <br />
  You can make it easier for new people to join the community by welcoming them and helping them find their way.

### Avoiding Burnout

Maintaining an open source project can be a lot of work, and many people do it alongside their 'day job'. It is essential to be mindful of the risk of burnout and take steps to keep the work manageable.

Decide on a reasonable time frame for responding to issues and pull requests, and include it in your documentation. If you are maintaining a personal repository in your spare time, it is okay to say a week.

If you are maintaining a company repository, state your working hours in the documentation and clarify that you respond only during office hours. Keep to these hours.
